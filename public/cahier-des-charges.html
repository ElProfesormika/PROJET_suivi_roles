1. Objet

Remplacer le registre papier des déplacements du personnel enseignant par une application web. Chaque mission conserve la date, la nature, le conducteur, les personnes transportées, le trajet, les horaires, le véhicule, les kilométrages et les remarques. Le responsable peut valider ou refuser. Les distances et les volumes servent au suivi.

L’application est en service en local. Le registre historique du professeur, de septembre 2012 à novembre 2018, est chargé dans la base mission_ujm.

2. Acteurs

RôlePérimètre
Enseignant Crée et consulte ses missions, transporte des collègues déjà inscrits dans l’annuaire, change son mot de passe. Il ne voit pas les missions des autres. Une mission validée ne peut plus être modifiée par lui.
Responsable Voit toutes les missions, valide, refuse ou remet en attente, avec un commentaire. Consulte les statistiques de l’ensemble du personnel. Peut supprimer une mission.
Administrateur Mêmes droits que le responsable, plus la création, la modification et la désactivation des comptes. Le dernier administrateur actif ne peut pas être désactivé.

Les contrôles sont faits sur le serveur. Changer l’adresse d’une mission qui n’appartient pas à l’enseignant renvoie une erreur 403.

4. Règles de gestion

  • La distance d’un trajet vaut kilometrageRetour − kilometrageDepart. Elle n’est pas enregistrée.
  • Les deux relevés sont tous les deux renseignés, ou tous les deux vides. Le retour ne peut pas être inférieur au départ.
  • Prendre le véhicule, c’est le kilométrage de départ. Rendre le véhicule, c’est le kilométrage de retour. Le formulaire propose le dernier kilométrage connu du véhicule.
  • Le type Velo n’a pas de compteur : les kilométrages restent vides. Les autres types (Megane, 3008) exigent les deux relevés.
  • La date d’arrivée peut être postérieure à la date de départ. Les heures ne sont comparées que lorsque le trajet tient sur une seule journée.
  • Une personne transportée doit déjà exister dans personne. Le conducteur n’est pas recopié dans la table d’accompagnement.
  • Les 1 425 trajets historiques sont au statut validé, avec le commentaire « Reprise du registre historique. »

5. Modèle de données

Les quatre tables du registre d’origine sont conservées : personne, vehicule, trajet, accompagner. Le mot de passe, les rôles et le circuit de validation ont été ajoutés. Le type du véhicule est un texte libre, comme dans le registre : Megane, 3008, Velo.

Annuaire

personne

Identité, civilité, courriel unique, empreinte du mot de passe, rôle, département, téléphone, compte actif. Neuf lignes : un administrateur, un responsable, sept enseignants.

Parc

vehicule

immatriculation, marque, type. Trois véhicules. L’immatriculation du vélo est vide, comme dans le fichier d’origine.

Registre

trajet

Nature, dates et heures de départ et d’arrivée, lieu, destination, kilométrages, conducteur (idPersonne), véhicule (idVehicule, facultatif), remarques. Ajouts : statut (en_attente, validee, refusee), validateur, date de validation, commentaire. Contraintes : l’arrivée n’est pas antérieure au départ ; les kilométrages sont cohérents ou absents.

Passagers

accompagner

Couple idTrajet + idPersonne. Soixante-quatre liaisons. La suppression d’un trajet retire ses accompagnants.

Catalogue

types_missions

Liste des natures proposées dans le formulaire, dont « Visite stagiaire » et « Visite alternant ». Le trajet enregistre le libellé dans nature.

6. Réalisation technique

  • PHP 8, architecture MVC, Bootstrap 5, MySQL 8, requêtes préparées PDO.
  • Sessions nommées, cookie HttpOnly, régénération d’identifiant à la connexion.
  • Contrôle d’accès par rôle, côté serveur.
  • Schéma : database/database.sql. Registre historique chargé par database/import_legacy.php.
Le graphique « six derniers mois » du tableau de bord est vide : les trajets s’arrêtent en 2018, et la fenêtre calculée est celle d’octobre 2026. Le graphique des statuts, lui, reflète les 1 425 missions validées.
